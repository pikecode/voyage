# 蘑说财务管理系统产品需求文档

版本：v1.0
日期：2026-08-27
范围：Web 后台管理端（阶段一、二）、微信小程序端（阶段三）
需求来源：《蘑说财务管理系统需求整理》思维导图、《蘑说财务管理系统 V1 需求文档》、T-04 交互原型

## 1. 需求背景

公司是连锁餐饮企业，旗下多个门店，全员已加入总公司钉钉，门店在钉钉中以「部门」区分。日常经营中产生三类财务数据，目前依赖人工在 Excel 中勾稽：

- 报销单据：员工在钉钉 OA 提交报销审批，涉及多个审批模板，钉钉提供 API 可同步单据数据。
- 银行流水：从网银导出，是资金实际发生的凭证。
- 营业收入：来自美团、抖音、扫码、现金等多个渠道，无系统对接，需人工录入。

人工勾稽的核心痛点是：报销单据和银行流水是两套独立数据，只有金额和日期可以参照，需要人工逐笔判断「这笔转账是哪张单据产生的」。门店多、单据多，效率低且容易错漏，月底出不了准确的门店财务报表。

本系统要解决的是：让这三类数据在系统内落地，通过金额匹配 + 人工确认建立单据与流水的关联关系，在此基础上按门店维度做报销数据分析和财务报表。

## 2. 产品目标

### 2.1 业务目标

- 三类数据一次落地，不再依赖 Excel 手工搬运。
- 单据与流水的关联关系可追溯、可回退，做账过程有据可查。
- 门店财务报表由系统生成，替代人工汇总。
- 股东可自助查看门店经营数据，不再依赖财务导表转发。

### 2.2 核心指标

- 单笔流水的匹配确认耗时。
- 系统推荐匹配的采纳率（推荐首位被确认的比例）。
- 月度做账周期（从数据齐备到封账的天数）。
- 未匹配流水与未对账单据的月末残留量。
- 报表生成后的人工返工次数。

## 3. 阶段划分

产品分三个阶段交付，每个阶段独立可用。

| 阶段 | 目标 | 交付内容 | 完成标志 |
|---|---|---|---|
| 阶段一 | 数据落地与匹配 | 钉钉同步、流水导入、匹配确认、分类归属、收入录入、门店账套 | 一个门店一个月的三类数据全部入库，关联关系确认完毕，账套可封账 |
| 阶段二 | 报表 | 门店财务报表、门店维度分析、仪表盘、导出 | 封账后自动产出该门店该月报表，数据与手工账一致 |
| 阶段三 | 小程序报表 | 股东端只读报表 | 股东可在小程序查看授权门店的经营数据 |

阶段一是全部后续能力的基础，数据模型和关联关系的设计必须在阶段一一次做对。阶段二不引入新的数据采集，只做读和聚合。阶段三不做账，只做展示。

## 4. 用户与角色

### 4.1 阶段一、二（Web 端）

- 财务做账人员：主要使用者，完成同步、导入、匹配确认、分类、收入录入、封账。
- 财务负责人 / 总部管理员：配置钉钉对接、字段映射、支出分类体系、供应商；查看全门店报表。

阶段一、二采用单一管理员密码登录，不区分账号角色。所有关键操作（修改归属账期、解除关联、封账、重开）记入操作日志，用操作可追溯替代权限隔离。角色与权限体系在阶段三之后再做。

### 4.2 阶段三（小程序端）

- 股东：只读查看被授权门店的财务报表，不参与做账。

## 5. 核心概念

| 概念 | 定义 |
|---|---|
| 门店 | 等于钉钉「部门」，由系统自动同步。可停用，不可删除；停用门店的历史账套保留 |
| 账套 | 一个门店一个月份的财务账，是做账和报表的基本单位，独立封账 |
| 报销单据 | 从钉钉 OA 同步的一张审批单，可包含多条支出明细行 |
| 支出明细行 | 审批单内的一条支出记录，是分类、供应商关联、金额分摊的最小单位 |
| 归属账期 | 一条支出计入财务报表的月份，可人工调整，与钉钉提交时间无关 |
| 匹配（对账） | 建立银行流水与业务数据（支出明细行 / 收入项）的关联关系，确认资金流向 |
| 封账 | 账套的完成标记，封账后禁止写入；可二次确认重开 |

## 6. 业务主流程

系统的核心是一条数据流水线，三类数据分别入库，再由人工建立关联。

```
钉钉 OA 审批   ──API 增量同步──┐
                              ├─→ 支出明细行 ──┐
网银导出 Excel ──批量导入────→ 银行流水 ──────┼─→ 人工匹配确认 ─→ 关联关系
                                              │        （金额为主、日期为参考的系统推荐）
多渠道经营数据 ──人工录入────→ 收入记录 ──────┘
                                                          ↓
                                              归属账期 + 门店 + 支出分类
                                                          ↓
                                              账套封账 ─→ 门店财务报表 ─→ 小程序展示
```

关键设计取向：系统只负责推荐，不自动确认关联。金额相同的单据可能有多张，日期也可能偏差，最终判断必须由做账人员完成，系统的职责是把候选范围收窄并让确认动作足够快。

## 7. 记账口径（贯穿全系统的基础规则）

以下五条口径决定了数据模型和报表结果，需在开发前确认。文档给出推荐方案，标注为「待确认」的需业务方拍板。

### 7.1 支出的入账时点

**推荐：权责发生制，以归属账期为准入账，与是否已匹配流水无关。**

一条支出明细行只要完成分类且设定了归属账期，即计入该月报表。匹配银行流水解决的是「这笔钱付了没有、从哪付的」，不改变入账月份。

由此产生两个独立维度，报表和列表都需要能分别筛选：

- 入账状态：已入账（有归属账期）/ 待归集（无归属账期）
- 付款状态：已匹配流水（已付）/ 未匹配流水（未付，构成应付）

这样跨月付款（8 月的食材 9 月付）能正确落在 8 月成本里，同时应付账款可以直接由「已入账未匹配」算出。

**待确认**：若业务实际按收付实现制（付款才算成本），则报表口径改为以流水月份入账，此时「未付」概念消失，供应商应付汇总功能同步取消。两者不可混用。

### 7.2 付款状态的判定

**推荐：匹配银行流水即视为已付，不设独立的「标记付款」动作。**

现金支付、老板私人垫付等无银行流水的支出，通过「手动录入支出」补录并标记付款方式为现金，视为已付。这样避免维护两套状态，也避免出现「已匹配但未标记付款」的歧义数据。

### 7.3 收入的匹配口径

**收入对账用实收金额匹配银行流水，报表营业收入用经营收入统计。**

营业收入录入时同时记录经营收入和实收金额，手续费 = 经营收入 − 实收金额，由系统自动计算。银行到账的是实收金额，因此匹配必须用实收金额，否则永远差一笔手续费对不上。

报表中的处理：营业收入取经营收入合计，手续费作为独立支出项列示，两者相减可回推实收。

### 7.4 关联关系的粒度

**统一到支出明细行级别。** 一笔银行流水关联的是一条或多条支出明细行，不是整张审批单。

原因：一张审批单内的多条明细可能分属不同支出分类、不同供应商，也可能分批付款。审批单在界面上仍作为聚合单位展示（勾选整单等于勾选其下全部明细行），但数据关系落在明细行。

审批单的对账状态由其明细行推导：全部已匹配 = 已对账，部分已匹配 = 部分对账，全部未匹配 = 未对账。

### 7.5 分摊与尾差

关联关系是多对多，需支持三种情形：

- 一对一：一笔流水对一条明细行，最常见
- 一对多：一笔流水对多条明细行（合并付款），各明细行分摊金额之和等于流水金额
- 多对一：多笔流水对一条明细行（分期付款），显示已付期数与剩余金额

尾差处理：分摊合计与流水金额允许存在差额，差额上限可配置（建议默认 ±1 元或 ±0.5%，取较大值）。超出上限时阻止确认；在上限内时，差额计入「手续费/尾差」科目，并在关联记录上留痕。不允许静默吞掉差额。

## 8. 阶段一：数据落地与匹配

阶段一是本次开发的主体，包含四条数据通道（同步、导入、录入、配置）和一个匹配工作台。

### 8.1 钉钉对接与单据同步

#### 8.1.1 API 绑定

配置企业内部应用的 appKey / appSecret，提供「测试连接」验证凭据有效性。凭据加密存储，界面不回显明文。

#### 8.1.2 审批模板管理

绑定成功后拉取企业全部 OA 审批模板列表。企业可能有几十个模板，其中只有少数几个与财务相关，因此模板默认全部停用，由管理员手动启用需要的模板。

模板列表字段：模板名称、模板编码、启用开关、字段映射状态、最后同步时间、手动同步按钮。

规则：
- 未启用的模板不参与任何同步和联动。
- 字段映射未完成的模板不允许启用，也不允许同步。
- 停用模板不删除已同步的历史数据，只停止后续同步。

#### 8.1.3 字段映射

不同审批模板的字段名称和结构各不相同，但做账时都要归集为标准的「支出项」，因此每个启用的模板都需要配置一次字段映射。

系统标准字段池：

| 标准字段 | 是否必填 | 说明 |
|---|---|---|
| 门店 | 必填 | 映射到钉钉部门，或审批单内的门店字段；决定单据归属哪个账套 |
| 支出日期 | 必填 | 业务实际发生日期，是归属账期的默认取值依据 |
| 金额 | 必填 | 支出明细行金额 |
| 支出详情 | 必填 | 支出内容描述 |
| 支出一级分类 | 选填 | 未映射时由人工在系统内分类 |
| 支出二级分类 | 选填 | 同上 |
| 申请人 | 必填 | |
| 凭证人 | 选填 | |
| 收款账户 | 选填 | 辅助匹配流水对手方 |
| 报销图片 | 选填 | 图片类凭证，可下载存储 |
| 报销凭证文档 | 选填 | Excel / Word / PDF 类凭证，受权限限制，见 8.1.5 |
| 备注 | 选填 | |

支出字段扩展：总部可自定义新增字段并与审批单接口字段关联。阶段一自定义字段只在单据详情中展示，不进入报表列（报表列固定，避免动态列带来的复杂度）。

#### 8.1.4 同步机制

- 手动触发增量同步，不做实时回调。每个模板独立同步、独立记录水位。
- 水位按审批单的最后修改时间推进，而非创建时间，避免遗漏「创建较早但近期才审批通过」的单据。
- 幂等：以钉钉审批单实例 ID 为唯一键，重复同步执行更新而非插入，重跑不产生重复数据。
- 表格型审批单需逐行解析明细，一张单据生成多条支出明细行。
- 同步结果反馈：新增数量、更新数量、失败数量与失败原因，失败可重试。
- 已同步单据在钉钉侧被撤销或驳回时，同步时标记为作废并从报表中剔除；若该单据已建立关联关系，需提示做账人员先解除关联。

#### 8.1.5 凭证存储与查看

- 图片类凭证：同步时下载到服务器磁盘，数据库存相对路径，保留缩略图和原图两级。
- 文档类凭证（Excel / Word / PDF）：钉盘下载权限 `Drive.DownloadInfo.Read` 属 OA 高级版专享且当前未开通，因此**阶段一不下载钉盘文档，界面显示占位并提示前往钉钉查看**。
- 阶段一的文档在线预览能力仅服务于「手动录入支出」时用户主动上传的凭证。钉盘文档预览待权限开通后在阶段三补做。

### 8.2 银行流水导入

#### 8.2.1 批量导入

支持网银导出的 Excel / CSV 文件。导入流程：上传文件 → 配置列映射（交易日期、金额、收支方向、摘要备注、对手方）→ 预览校验 → 确认导入。

导入去重是硬要求。同一份网银文件重复导入会直接污染报表，规则：
- 以（交易日期 + 金额 + 收支方向 + 摘要 + 对手方）计算指纹，命中已有记录时标记为疑似重复，默认不导入并在预览中列出，由用户决定是否强制导入。
- 每次导入生成批次记录，支持整批撤销（批次内已建立关联的流水不允许撤销，需先解除关联）。

导入后的流水默认状态为未匹配。

#### 8.2.2 单笔录入

弹窗表单单笔录入，字段：交易日期、所属门店账套、金额、收支方向、备注。支持连续录入多笔，逐行校验。

#### 8.2.3 流水列表与查询

列表字段：交易日期、所属账套、金额、收支方向、摘要备注、匹配状态标签。支持行内编辑即改即存（已匹配的流水禁止改金额和方向）。

筛选：月份（默认上一个月）、匹配状态、收支方向。

**金额容差查询**：输入金额后按容差范围筛出流水，按接近度排序。容差规则为 `max(金额 × 5%, 下限)` 并设置绝对上限，避免大额流水容差过宽（10 万的 5% 是 5000，会捞回大量噪音）、小额流水容差过窄。具体阈值可配置。该查询同时服务于流水页查找和匹配时的辅助查找。

### 8.3 营业收入录入

#### 8.3.1 收入渠道

预置渠道：美团团购、美团点评买单、抖音团购、现金收款、扫码收款、商场代金券。支持自定义新增渠道，自定义渠道与预置渠道行为一致，数据同样进入报表营业收入。

每个渠道需配置「是否产生银行流水」。现金收款、商场代金券等不产生银行到账的渠道标记为无需对账，否则这些收入会永久挂在待对账队列，污染待办统计。

#### 8.3.2 录入编辑器

每个渠道点进入后弹出编辑器，按当前账套月份的日期升序自动生成全部行（1 到当月最后一天）。

列：日期、经营收入、实收金额、手续费（只读）、手续费率（只读）、备注、行状态、删除。

批量录入能力：
- Excel 粘贴：光标定位到某日某列后粘贴多行多列数据，按天向下、按列向右填充；支持千分位格式；超出月底自动截断。
- 起止日 + 金额批量填充。

自动计算：手续费 = 经营收入 − 实收金额；手续费率 = 手续费 / 经营收入。

行状态机：未录入 → 待保存 → 已保存 → 已修改。存在未保存数据时关闭编辑器需二次确认防丢失。

### 8.4 支出分类与供应商配置

#### 8.4.1 支出分类

两级分类体系（大类 → 小类），一二级均支持新增、改名、排序、停用。全公司统一，所有门店共用。

二级分类可标记「需关联供应商」（如食材类），该标记决定分类时是否出现供应商选择。

停用或删除分类不影响已使用该分类的历史账目，历史记录保留原分类名。

#### 8.4.2 供应商

字段：供应商名称、联系人、联系手机、账期（月结 / 半月结 / 周结 / 现结）、结账日（每月几号 / 每周几，现结不填）、关联门店。

关联门店规则：默认关联所有门店；也可指定若干门店，此时只对这些门店生效，门店端供应商列表按此过滤。

应付汇总：按 7.1 口径，未付 = 已入账且未匹配流水的支出金额合计。在总部供应商页展示全部门店口径，在门店端供应商列表展示本门店口径。阶段一不做付款提醒。

### 8.5 单据管理

单据管理解决两件事：把支出归到正确的月份，把支出归到正确的分类和供应商。这两步是报表准确的前提，需在匹配之前或匹配过程中完成。

#### 8.5.1 单据列表

范围为当前账套（门店 + 月份）的全部审批单，跨模板混合展示。

列：审批编号、申请人、模板名称、归属账期、申请日期、支出详情、金额、审批状态、报销图片（缩略图，点击展开）、报销凭证文档、对账状态（未对账 / 部分对账 / 已对账，已对账显示对应流水月份）。

筛选：模板、对账状态、是否已分类、是否已设归属账期。

#### 8.5.2 归属账期调整

弹窗选择归属账期月份。默认取支出日期所在月份，可人工改到任意未封账月份。

目标月份已封账时阻止修改，提示需先重开该月账套。这一约束是为了避免已出的报表被静默改动。

#### 8.5.3 单据详情

点击列表行弹窗展示，不离开当前页。左侧字段区（审批编号、模板、申请人、门店、提交时间、归属账期、总金额、审批状态、收款账户、备注），右侧凭证区（图片可放大，文档按 8.1.5 处理）。

下方为支出明细行表格，展示日期、支出详情、金额、支出分类、供应商、匹配状态。

#### 8.5.4 明细行批量分类

一张审批单常包含多条支出明细，需支持勾选多条明细行后批量设置支出分类（二级）。当所选分类标记为「需关联供应商」时，弹出供应商下拉（仅列出对该门店生效的供应商），选择即建立关联。

列表页也支持跨单据勾选后批量分类，用于处理同类型的大批单据。

### 8.6 匹配工作台

这是阶段一的核心界面，做账人员的主要工作时间在这里。

布局：左侧为当前账套的银行流水列表（带匹配状态标签），右侧为匹配操作区。选中左侧一笔流水后，右侧按收支方向展示对应的匹配流程。

#### 8.6.1 支出流水匹配

1. 系统在当前账套内搜索未匹配的支出明细行，以金额为主、日期为参考计算匹配度，按置信度降序推荐。
2. 推荐算法采用三档打分（沿用既有桌面版基线）：金额完全一致得 90～98 分（日期越近分越高）；金额在容差内相近按差额递减；分期场景按 `90 − 3 × 日期差天数`。
3. 每条推荐带勾选框和「详情」按钮，详情弹窗内容见 8.5.3，凭证可再叠一层查看器，全程不跳页。
4. 支持勾选多条明细行分摊一笔流水，界面实时显示已选合计、流水金额、差额。差额超出 7.5 定义的上限时禁止确认。
5. 支持一条明细行被多笔流水分期匹配，显示「已付 N 期 / 剩余待付金额」。
6. 确认关联后：流水转为已匹配；对应明细行记录付款流水与分摊金额；审批单对账状态按 7.4 重新推导。
7. 确认成功后 1.5 秒自动跳转到下一笔未匹配流水，保持连续作业节奏。

辅助操作：
- 手动搜索关联：推荐列表无结果时，按审批编号或金额搜索后手动关联。
- 拒绝匹配：标记「不是这笔」，该流水与该明细行的组合不再出现在推荐中。
- 无单据支出：支持手动录入支出，字段为支出日期、支出详情、支出分类（二级）、金额、付款方式、支出凭证（可上传图片和文档）；录入后与当前流水关联。
- 解除关联：唯一的逆操作，二次确认后回退流水状态、明细行付款记录、审批单对账状态和相关统计。

#### 8.6.2 收入流水匹配

1. 选择收入渠道。
2. 选择该笔到账对应的经营日期范围（如 8 月 10 日至 22 日）。
3. 系统汇总该渠道该范围内的实收金额，与流水金额比对并显示差额。
4. 确认后建立关联，范围内的收入日标记为已被占用。
5. 已被占用的收入日在后续选择范围时高亮提示，防止重叠区间被重复入账。

#### 8.6.3 匹配约束

- 匹配只在同一账套内进行，跨门店、跨月份不允许直接匹配。跨月场景通过调整归属账期解决。
- 账套封账后禁止新增和解除匹配。

### 8.7 门店账套管理

#### 8.7.1 账套列表

顶部为年月选择器，默认当前月份的上一个月（当月做上月的账）。搜索栏支持按门店名称模糊搜索。

每个门店一张卡片，显示门店名称、所选月份的账套状态标签（封账 / 待做账）、进入账套按钮、封账或重开按钮。

门店数据由钉钉部门自动同步，可停用不可删除。停用门店不出现在默认列表中，历史账套保留可查。

#### 8.7.2 账套内导航

进入账套后，顶部固定显示当前门店和月份并支持切换月份，下属六个功能页：账套首页、营业收入、银行流水、匹配工作台、单据管理、供应商列表。

当前账套（门店 + 月份）是全局上下文，所有子页面的数据范围由它决定，不允许在无账套上下文的情况下进入子页面。

#### 8.7.3 账套首页

展示当月经营数据概览：各渠道收入合计、流水收入与支出合计、待匹配流水笔数、未分类明细行数、未设归属账期单据数。每个数据块提供按钮进入对应功能页。

#### 8.7.4 封账

手动点击封账，二次确认后账套状态转为封账，禁止一切写入（收入录入、流水导入、匹配、分类、归属账期调整）。

封账后可二次确认重开，重开后状态回到待做账、数据可编辑。封账和重开均记入操作日志。

### 8.8 门店端供应商列表

账套内的供应商视图，仅展示对该门店生效的供应商。

- 列表显示供应商信息、账期、本门店口径的未付与已付金额。
- 点击供应商查看已关联到该供应商的支出明细行。
- 提供反向关联入口：列出该门店未关联供应商的需关联类支出明细行，可在此手动关联。

### 8.9 历史数据迁移

既有桌面版（Python + SQLite）已积累真实数据，需迁移到新系统：

- 1144 张报销单、4039 张凭证图片。
- 既有 15 张表结构作为设计参考，新系统需扩展供应商表、支出明细行关联表、分摊金额字段、操作日志表。
- 既有钉钉同步模块（两阶段同步、水位、幂等）和字段映射解析逻辑可复用。
- 既有对账三档打分算法作为推荐置信度基线。

迁移需明确：旧分类体系如何映射到新的两级分类、历史单据的归属账期如何补齐（建议按支出日期回填）、历史关联关系如何转换为明细行级关联。迁移脚本需可重复执行且支持校验比对。

### 8.10 操作日志

阶段一采用单一密码登录，无法通过账号追责，因此操作日志是必要的补偿措施。

记录范围：归属账期调整、支出分类变更、供应商关联变更、匹配确认、解除关联、封账、重开、流水导入与批次撤销、流水编辑、钉钉同步。

每条记录包含操作时间、操作类型、操作对象、变更前后值。日志只读不可删。

## 9. 阶段二：报表

阶段二不引入新的数据采集，只对阶段一落地的数据做聚合、展示和导出。前提是阶段一的门店、归属账期、支出分类、关联关系四项数据齐备且准确。

### 9.1 通用规则

- 筛选维度：门店 + 月份，月份口径统一为归属账期。
- 数据来源：营业收入取各渠道经营收入合计；支出取归属账期在所选月份、且已完成分类的支出明细行（含审批单支出和手动录入支出）。
- 未分类的支出明细行不进入分类汇总，但需在报表页显著提示数量，避免遗漏导致报表少计。
- 未封账账套的报表标注「数据未最终确认」。

### 9.2 收支明细表

按时间顺序列出当月全部收支条目，是报表的最细粒度视图。

列：日期、类型（收入 / 支出）、项目（收入渠道名 / 支出详情）、分类、供应商、金额、关联流水、凭证。

行为：点击支出行展开原始单据详情与凭证；点击关联流水查看流水信息。合计行显示收入合计、支出合计、净额。

### 9.3 利润汇总表

门店当月的经营结果概览。

行项目：营业收入（按渠道明细展开）、手续费、支出合计（按一级分类展开）、利润。

列：本月金额、占营业收入比例、上月金额、环比。

### 9.4 分类汇总表

按支出分类维度汇总，用于成本结构分析。

层级：一级分类汇总，可展开二级分类明细。列：分类名称、金额、占支出比例、笔数。需关联供应商的分类可再下钻到供应商维度。

### 9.5 门店报销数据分析

基于门店维度的分析视图，是本系统区别于单纯记账工具的价值点。

- 单门店趋势：近 N 个月的收入、支出、利润、各分类成本走势。
- 支出结构：单门店的分类占比及月度变化。
- 供应商分布：单门店各供应商的采购金额与占比。
- 异常提示：某分类成本环比波动超过阈值、某月缺少常规支出（如缺少房租）、单据金额显著偏离历史均值。

跨门店对比报表放在阶段三之后，阶段二先满足单门店纵向分析。

### 9.6 导出

导出为 HTML 交互报表，可在浏览器离线打开。导出内容包含三张报表，支持点击支出条目弹窗查看报销详情与凭证（凭证以内嵌方式打包，保证离线可看）。

## 10. 阶段三：小程序报表

### 10.1 定位

微信小程序端仅供股东查看门店财务报表，不做账、不录入、不修改任何数据。数据完全来自 Web 端已封账的账套。

### 10.2 功能范围

- 微信登录，由管理员在 Web 端配置股东账号及其可查看的门店范围。
- 门店列表：展示有权限的门店及最近月份的核心指标。
- 门店报表：营业收入、支出合计、利润、分类占比，以图表为主。
- 月份切换与近 N 月趋势。
- 只展示已封账月份的数据，未封账月份不可见，避免股东看到过程数据。

### 10.3 阶段三同期补做

- 自定义角色与权限配置（Web 端）。
- 供应商付款提醒。
- 独立应付账款页面。
- 跨门店对比报表。
- 钉盘文档类凭证下载（待钉钉权限开通）。

## 11. 非功能需求

### 11.1 部署与环境

- 国内云服务器部署，HTTPS 访问。
- 凭证文件存服务器磁盘，数据库存相对路径。
- 数据库与凭证目录定期备份，支持恢复演练。

### 11.2 数据量级与性能

- 每年数千张审批单、数千张凭证图片，单管理员使用，并发极低。
- 千行级列表滚动和 Excel 粘贴填充需流畅无卡顿。
- 报表查询响应控制在秒级。

### 11.3 安全

- 钉钉 appSecret 加密存储，界面不回显。
- 登录密码可修改，会话过期需重新登录。
- 凭证文件不可通过猜测 URL 直接访问，需鉴权后下发。

### 11.4 交互约定

以下交互规则全局统一：

- 不可逆操作（封账、解除关联、删除、批次撤销）一律二次确认。
- 存在未保存数据时关闭弹窗需防丢失确认。
- 轻量反馈用 Toast，不打断操作流。
- 匹配确认后自动跳转下一笔，保持连续作业。
- 行内编辑即改即存。

## 12. 待确认事项

| 编号 | 事项 | 影响面 | 文档推荐 |
|---|---|---|---|
| Q1 | 支出入账采用权责发生制还是收付实现制 | 数据模型、报表口径、应付账款是否成立 | 权责发生制，以归属账期为准（7.1） |
| Q2 | 是否需要独立的「标记付款」动作 | 供应商应付汇总的准确性 | 不需要，匹配流水即视为已付（7.2） |
| Q3 | 手续费在报表中作为独立支出项还是收入抵减 | 利润表结构、营业收入口径 | 独立支出项，营业收入取经营收入（7.3） |
| Q4 | 分摊尾差的容忍上限和差额去向 | 匹配确认能否通过、差额科目设置 | ±1 元或 ±0.5% 取大，计入尾差科目（7.5） |
| Q5 | 单据的门店归属从钉钉部门取还是从审批单字段取 | 字段映射设计、账套归集准确性 | 优先取审批单门店字段，缺失时回落到申请人部门 |
| Q6 | 是否存在总部集中采购需分摊到多门店的场景 | 是否需要跨门店分摊模型 | 需业务方确认；若存在，需在阶段一预留分摊字段 |
| Q7 | 容差查询的容差下限与绝对上限取值 | 推荐结果的噪音水平 | 需结合真实流水数据标定 |
| Q8 | 历史数据的归属账期回填规则 | 迁移后历史报表的正确性 | 按支出日期所在月份回填 |
